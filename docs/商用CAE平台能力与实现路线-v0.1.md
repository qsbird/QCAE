> 历史讨论：本文件保留当时的分析与估算；当前开发依据为 [设计基线1.0](baseline/README.md)。冲突时不沿用本文件旧范围。

> 范围更新：用户已将 P0 改为本地中小模型、底层能力优先，服务器/亿级实现后置。本文旧路线与预算仅作历史研究记录；当前依据见 [P0 本地平台可行性分析](P0本地平台可行性分析-v0.2.md)。

承接已确认条件：普通电脑客户端、服务器处理大模型；导入既有亿级模型，查看/选择/分组/局部修改；允许 LOD 与渐进细化，最终选择和编辑准确；Nastran 单模板；必要几何网格功能；统一 undo/redo。客户端桌面或浏览器先比较再决定。

## 1. 如何理解商软的平台能力

平台能力让工程师能够找到对象、理解关系、组织工作、批量修改、检查错误、恢复操作和复用流程。它既包括界面，也包括界面背后的数据与操作语义。

本报告以 HyperMesh、ANSA、Femap 的官方公开资料为参照。以下能力清单是对行业产品能力的归纳，不表示所有软件、版本和授权包都具有完全相同功能。企业数据/流程管理可能需要独立产品或连接器；这些资料也不能证明其亿级远程编辑性能。

## 2. 可以直接核验的商软例子

- HyperMesh Model Browser 提供实体组织、属性查看/编辑，以及 INCLUDE 视图与编号范围；这说明模型管理已经超出普通文件树。[官方文档](https://help.altair.com/hwdesktop/hwx/topics/user_interface/browser_model_overview_c.htm)
- HyperMesh Model Checker 提供检查执行、失败实体定位、手动/自动修正和报告输出，形成发现到处理的工作流。[官方文档](https://help.altair.com/hwdesktop/hwx/topics/user_interface/model_check_run_t.htm)
- HyperMesh 2025 Python API Recording 可把交互操作转成参数化 Python，文档也列出选择录制的覆盖限制。[官方文档](https://2025.help.altair.com/2025/hwdesktop/pythonapi/hypermesh/hm_recording.html)
- ANSA 官方页面列出可定制环境、模型比较与更新、Task Manager 和 INCLUDE 配置能力。[官方页面](https://www.beta-cae.com/ansa.htm)
- ANSA 的数据管理资料描述零件/子系统的版本与表示库、PDM 接口及与 SPDRM 的连接；这是更高层的企业工作流能力，不能全部当作基本界面控件。[官方资料，较早发布，作为能力类别依据](https://www.beta-cae.com/brochure/ansa_data_management.pdf)

- Femap 官方示例介绍按属性等条件组织 Groups、局部显隐、剖切和邻域扩缩，体现了分组与观察范围之间的联系。[Siemens 官方示例，2021](https://blogs.sw.siemens.com/simcenter/machine-frame-digital-simulation-crafting-an-efficient-fea-workflow-part-2/)
- Femap 2023 的官方说明涉及 Command Finder、Teamcenter 文件管理与分析任务监控；2512 继续改进图形、显示和选择。[2023 官方说明](https://blogs.sw.siemens.com/simcenter/simcenter-femap-2023/)、[2512 官方说明，2026 年发布](https://blogs.sw.siemens.com/simcenter/whats-new-in-simcenter-femap-2512/)
- Femap 的 Model Info、Entity Editor、Data Table、API 和多步 Undo 可在其较早官方白皮书中核验；这仅证明长期能力，不承诺当前版本的细节，也没有据此推断自动保存或 Undo 的崩溃恢复语义。[2014 官方白皮书](https://www.plm.automation.siemens.com/en_us/Images/6579_tcm1023-5013.pdf)

## 3. 平台能力清单及建议范围

P0：首个可用工程版本必须有基本闭环。P1：生产效率与成熟度提升。P2：企业化或高级能力，按实际需求进入。优先级是本项目建议，尚非用户确认的完整范围。

| 能力 | 成熟平台用户期待的操作 | 本项目实现重点 | 优先级 |
|---|---|---|---|
| 工作区与命令发现 | 停靠面板、多视图、布局保存、右键、快捷键、搜索命令、偏好 | 全局动作定义、焦点规则、布局状态；先只提供必要工作区 | P0 |
| 模型组织 | 部件/装配、材料/属性、集合、INCLUDE；多种查看角度 | 一套实体关系、多种查询视图；客户端懒加载，服务器分页 | P0 |
| 查找与选择 | ID/名称/属性搜索，框选/区域选，隐藏与穿透选择，反选、邻接扩展、保存集合 | 统一选择语义与服务器索引，最终选择对应精确实体 | P0 基础，P1 高级 |
| 显示管理 | 隔离/恢复、颜色、透明度、剖切、标签、标准视图、书签、测量 | 全局 LOD 与局部精确显示；符号/标签有数量预算；联动高亮 | P0 基础，P1 增强 |
| 属性与表格编辑 | 批量编辑、排序/筛选、混合值、引用跳转、错误提示 | 卡片 schema + 引用关系；批量事务，不能每单元远程往返 | P0 |
| 模型引用与依赖 | 查看材料影响哪些属性、属性影响哪些单元；定位缺失引用 | 正向/反向引用索引；删除/替换前计算受影响范围 | P0 |
| Nastran 分析准备 | 材料、属性、坐标系、载荷、约束、工况、编号、导入导出 | 选定方言及卡片清单；字段编辑、校验与序列化使用同一语义 | P0 限定子集 |
| 工程与会话 | 保存/另存、最近项目、自动恢复、工程设置、会话恢复 | 工程模型与个人视图状态区分；持久化原子提交、兼容性与恢复 | P0 |
| 撤销、重做与历史 | 连续编辑合并、批量操作整体撤销、保存点、历史查询 | 服务器权威事务、差量/块历史、内存与磁盘配额 | P0 |
| 检查与问题处理 | 质量检查、重复/孤立对象、引用检查、定位、修正、复查、报告 | 问题对象含规则、实体、版本、严重度；修复经过同一命令系统 | P0 基础，P1 规则库 |
| 长任务与运行管理 | 进度、取消、批处理、失败原因、日志、后台操作 | 任务状态机、取消边界、版本一致性、资源配额、会话恢复 | P0，本项目特有高优先级 |
| 脚本与扩展 | Python/API、命令录制、批处理、参数化工具、自定义菜单 | UI、脚本、批处理走同一业务命令；先稳定 API，再完善录制与插件 | P1，底层接口从 P0 设计 |
| 工作流模板 | 固化导入—检查—修复—导出流程，重复运行，参数与结果记录 | 先顺序脚本/模板，再考虑可视化流程图；自动修复需明确事务边界 | P1 |
| 模型比较与更新 | 零件差异、属性变化、替换零件、模型变型、变更追踪 | 先稳定 ID 下的字段/连接差异；几何匹配和跨重编号匹配后置 | P1/P2 |
| 报告与交付 | 模型统计、检查清单、截图、可重复生成报告、导出包 | 从同一模型版本读取，记录来源与检查配置 | P1 |
| 企业库与协作 | 零件/材料库、版本、权限、发布、PDM/PLM/SDM 对接 | 首版仅项目访问和单文档单写者；库管理与协同合并后置 | P2 |

本项目的远程任务、断线恢复、会话隔离等是部署条件推导出的需求，不声称三款桌面商软都原生提供同样机制。

## 4. 成熟交互的单位是工作流程

建议用以下场景定义平台完整度：

> 搜索指定材料 → 找到使用该材料的属性 → 定位关联单元 → 在三维视图隔离 → 按条件缩小选择 → 批量修改 → 检查受影响区域 → 撤销/重做 → 保存 → 导出。

需要同时满足：

- 模型树、表格、三维视图和属性面板使用一致实体与选择状态。
- 表格显示混合值时，用户能明确知道修改的是哪个字段、影响多少实体。
- 大选择集保留在服务端，客户端获取结果句柄、数量和当前页，不下载几千万个 ID 来渲染列表。
- 选择集区分“固定成员快照”和“动态条件查询”；事务必须绑定模型版本与确定的目标，避免查询结果变化造成误编辑。
- 检查结果指向产生结果时的模型版本；模型修改后应失效或标为待复查，不能继续显示成已通过。
- 屏幕上的高亮预览与最终精确选择状态区分，避免低精度代理导致误操作。

仅分别做出树、表格、视口并不能形成上述能力，工作量集中在它们共享的语义。

## 5. 建议的七项公共基础能力

以下是自研路线建议，不是在推断商软内部实现。

### 5.1 文档与实体模型

平台拥有稳定内部 ID、Nastran 外部编号、部件/集合、引用关系、坐标系和模型版本。稠密数组按块存储大规模节点/连接，属性与元数据采用适合查询的结构。

第三方几何/网格对象只在适配器内出现。模型结构、INCLUDE 文件结构、显示分组是不同维度，应能互相映射，不能强迫共用一棵树。

### 5.2 卡片与属性 schema

对限定 Nastran 卡片定义字段类型、默认值、引用、约束、显示名称和读写规则，复用于属性面板、表格、校验和脚本接口。特殊卡片仍可使用手写编辑器，不必强迫所有功能都由通用配置生成。

Nastran 的一致单位约定需作为工程元数据处理，不能假设 BDF 自动携带完整单位语义。缺失或不确定的单位需要明确展示。

### 5.3 查询与选择

统一承接 ID、属性、空间和拓扑查询；结果带模型版本，可进行交并差、计数和分页。渲染拾取返回的 ID 必须经过精确模型解释。

若新增选择条件，树、表格、批处理和脚本应共同受益，而不是分别实现一遍。

### 5.4 命令与事务

所有修改通过同一条路径：校验输入与版本 → 确定目标 → 计算变更 → 原子提交 → 记录撤销数据 → 发送变更通知。

命令要有明确参数和可重试标识，但不必首期引入完整事件溯源框架。数据撤销日志、用户可读历史、可复用脚本是三种不同产物：撤销需要精确恢复，脚本需要参数化语义，不能彼此替代。

### 5.5 任务调度

导入、检查、局部重网格和导出运行于后台任务。任务至少区分排队、运行、取消中、成功、失败；提交与计算分离。长任务用稳定模型快照，完成时检测版本冲突。

初版可在单个服务器实例内调度，不因为有七项公共能力就拆成七个微服务。数据核心和渲染进程是否分离，以复制成本、稳定性和资源竞争实测为依据。

### 5.6 显示适配与状态同步

渲染读取模型快照和局部变更，维护可重建的显示缓存。客户端发送相机、选择、命令和视图设置；服务端回传图像、摘要和变化。

消息至少关联请求、会话、模型版本；显示拾取还要关联对应画面的相机/帧状态。慢请求不能覆盖新状态，断线重试不能重复提交修改。

### 5.7 持久化与恢复

工程快照、事务历史、缓存和个人会话状态分别管理。缓存可以重建，已提交模型不能丢失。崩溃恢复与普通 undo 不完全相同；不能把“写一个操作日志”视为都已实现。

## 6. 实现顺序与每阶段退出条件

每阶段保留前阶段的规模、正确性与网络基准，不能先完成小模型全部功能再开始考虑亿级。

| 阶段 | 核心交付 | 进入下一阶段的证据 |
|---|---|---|
| A：定义基准 | 确定规模口径、模型类型、服务端/客户端最低硬件、网络条件、核心操作和卡片子集 | 有真实/合成样本、固定操作脚本和可测性能指标 |
| B：风险原型 | 最少 Nastran 子集导入、远程浏览、精确选择、单字段修改、撤销与重做、保存重开 | 同一闭环通过百万→千万→亿级数据；记录 RAM/VRAM、输入延迟、峰值历史体积；断线无重复修改 |
| C：可用平台 | 模型树、选择过滤、隔离显示、属性/表格编辑、集合、工程保存、诊断与任务面板 | 用户能独立完成一次真实局部修改任务；所有入口共享事务，错误可定位 |
| D：生产效率 | 扩充已选 Nastran 卡片、批处理、脚本 API、检查模板、报告、命令参数化 | 同一任务可通过交互或脚本复现，回归样本语义一致；大操作失败/取消不破坏工程 |
| E：高级管理 | 模型比较、部件替换、表示/变型管理、企业库与外部系统接口 | 有真实团队流程证明收益，且复杂性不破坏核心性能和版本一致性 |
| 持续产品化 | 安装/部署、协议与工程格式迁移、监控、恢复测试、驱动/浏览器兼容、文档 | 可发布、可升级、可定位故障，性能与正确性无回退 |

阶段 B 必须包含真实编辑与撤销；只完成漂亮的远程查看器，无法验证后续最难的事务和更新成本。阶段 B 可以采用简单按钮和最小面板，同时对桌面/浏览器进行交互验证，避免先投入完整界面。

建议第一条闭环限定为：**打开模型 → 按属性选择 → 隔离局部 → 修改一个属性字段或小范围节点 → undo/redo → 保存重开 → 导出并核验**。集合编辑、坐标修改和拓扑修改的数据成本不同，后续分别扩展。

## 7. 组件如何进入这条路线

承接首份预研中的候选：

- Qt/Qt ADS：桌面外壳；若最终浏览器路线胜出，不建设重复的完整桌面客户端。
- trame：远程显示与交互原型；产品化可继续评估，但不让其 UI 状态替代业务模型。
- VTK/ParaView：科学显示与远程显示基线；适配自研模型、评估 filter 临时数据与局部更新。
- OCCT：必要几何服务；Netgen/Gmsh：必要网格后端，按需求与许可选择。
- HDF5/SQLite 等：数组存储或元数据候选，事务边界仍由平台设计。

组件事实、许可与限制见前文档：[CAE 需求分析与组件预研 v0.1](CAE需求分析与组件预研-v0.1.md)。平台仍需自研 Nastran 文档语义、统一查询/选择、业务命令、undo/redo 数据管理与远程一致性。

## 8. 如何处理工期与预算

当前不宜按“商软有多少菜单”估算工期。工作区控件相对容易复用，查询选择、可靠事务、远程交互、大规模持久化才是关键路径。

建议估算单位是具有性能和正确性验收的工作流程，例如“跨 INCLUDE 选择并批量改属性且可撤销”。每个流程再拆成 UI、查询、事务、显示更新、格式校验及测试，避免只统计可见按钮。

若主要由个人开发，应先完成阶段 B/C 的受限闭环。若进入团队开发，基本专业分工是模型/格式、事务/存储、显示/远程交互、客户端 UX，以及 CAE 验证；是否由不同人员承担取决于团队规模，职责不能缺失。

先前 token 预算仍只是宽区间占位，不因本次列出商软能力就自动扩大实施范围。完成阶段 B 后，用实际闭环消耗和缺陷数据估算 C/D；若要包括 E 的企业库、PLM 和多人协作，则需单独估算，不应混入“平台完整”的默认含义。

## 9. Undo/redo 的商软边界与本产品承诺

Altair 当前公开帮助页仍说明部分操作不可撤销，存在历史清除及内存限制。因此不能把商软对标写成“任何操作无限撤销”。[官方 Undo/Redo 文档](https://help.altair.com/hwdesktop/hwx/topics/user_interface/undo_redo_t.htm)

建议本产品为每个修改命令声明撤销能力和预估历史成本：常规编辑必须可撤销；批量/拓扑修改具有受配额约束的撤销策略；导出文件、外部作业提交等外部动作不纳入普通模型撤销语义。该建议仍需作为需求边界确认。

原生几何/网格库不支持增量撤销时，可以在受限局部范围保存变更前后块；不能因此复制整个亿级模型，也不能静默清空全部历史。
