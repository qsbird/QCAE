# 以简单场景验收平台骨架的工程化重构提案

状态：用户已同意方案方向，已完成C1/C2限定范围；响应用户关于“先建设完整代码组织与核心链路，再低成本扩展功能”的目标。本文保留重构起点与完整目标，不将目标目录、接口名称或验收要求作为已实现声明。当前证据见[C2记录](../engineering/c2-validation.md)，剩余缺口见[扩展审查](../engineering/extensibility-audit-c2.md)，接续顺序见[开发计划](../baseline/development-plan.md#c2之后的接续计划)。

## 参考架构对齐目标

用户进一步要求至少在架构模块设计上全部对齐ArcherprePublic，并在部分平台机制上超过。原提案不足以单独保证此目标；现以[Archer架构覆盖矩阵与补充验收](archer-architecture-parity.md)作为本提案的必要补充。实施前须完成参考库存/缺项审计；不能只用梁场景或目录数量声明全部对齐。该补充增加参数/坐标、分析工况、检查修复、结果、交互工具、完整能力包贡献和配置支撑的责任设计。

检查点与完成预期以[SK-01—14验收合同](../baseline/skeleton-acceptance.md)为准；同意方案不等于检查点已经通过。

## 1. 重构目标与边界

下一阶段的交付单位调整为“平台骨架及其扩展机制”。一个小场景应经过同一套模型、操作、后台任务、事务、历史、存储、查询、显示及客户端通路。新增功能时，开发者主要理解所属功能包和公开契约。

低成本扩展的具体含义：

- 新增普通操作时，允许修改功能处理器、操作定义、对应测试及必要UI入口；不修改提交协调器、历史引擎、SQLite提交逻辑或传输帧处理。
- 新增实体字段时，允许修改类型声明、语义校验及版本迁移；序列化、字段遍历、基本表单/协议转换不再各维护一份字段清单。
- 新增受支持拓扑时，修改拓扑/实体定义、相应算法、显示投影及格式适配；通用事务和恢复不感知“三角形”或“梁”。
- 新增物理领域仍需要领域设计。新增几何内核仍需要拓扑身份及数据映射，不能承诺全部变成配置操作。
- 编译期静态注册足够服务个人项目。暂不建设动态插件ABI、通用可视化工作流编辑器、分布式运行时或任意JSON属性数据库。

代码量随功能增长；骨架的完成标准是扩展改动可定位、公共机制稳定和失败路径可验证。

## 2. 重构前实现的具体问题

下表记录M2/M3阶段的重构起点；C1/C2已解决其中部分数据、模块和后台任务问题，当前未完成项以扩展审查及实施记录为准。

| 位置/机制 | 当前问题 | 调整方向 |
|---|---|---|
| `src/`、`include/qcae/`平铺 | 目录不能表达业务归属和公开/私有边界 | 以少量可构建模块和功能包组织，模块外只允许公开接口 |
| `qcae_core` | 文档、应用协调、查询、历史、格式化状态都在同一目标中 | 分离实际依赖方向，检查真实include/link，而非仅检查设计JSON |
| `model.hpp`、`model.cpp`、`state_codec.cpp`、`model_delta.cpp` | 实体及字段清单多处维护 | 一份强类型实体/字段目录驱动机械遍历、记录编码及历史路由 |
| `MemoryApplication` | 工程生命周期与具体编辑操作共处 | 生命周期、会话、提交协调和具体handler分离；保留兼容门面过渡 |
| 操作描述＋`supported()`＋IPC分支 | 描述、可用性、参数解析和执行相互独立 | 操作注册项绑定类型契约、handler和能力条件，统一分发 |
| 预览候选、历史差量 | 复制整个Data/Model；差量以容器字段序号和位置表达 | 只读快照＋受控编辑overlay；ChangeSet以稳定记录键表达 |
| `IWorkspaceStore::commit(payload)` | 通用性停留在整份字节封装，每次写入完整状态 | 增加有界记录/块批量提交，在同一事务内写数据、历史及操作事实 |
| 几何/网格归属 | Model有节点/梁，没有独立Mesh与几何源归属对象 | 分离Geometry、Mesh、Organization和AnalysisScope |
| Qt窗口＋桌面专用client | 窗口承担流程编排，CLI与GUI协议处理重复 | 公共客户端SDK、控制器/ViewModel和功能UI贡献项 |
| 长任务与产物 | 同步功能预览替代了部分未来运行链 | 用一个真实小任务完成队列、进度、取消、版本及产物发布闭环 |
| 当前验收 | 梁场景与故障检查已有证据，扩展成本缺少验收 | 增加字段、操作、拓扑三个“扩展练习”，检查改动边界 |

需要保留的成果：真实的文档/Epoch/Revision约束、幂等、提交后发布顺序、保存意图与恢复校验、工程锁、CLI/GUI共享状态、只读RenderPacket以及既有回归夹具。重构不以丢弃这些行为作为捷径。

## 3. 目标代码组织

建议采用模块化单体和静态组装。以下目录是迁移目标，不要求一次创建所有空目录或每个子目录建立一个库。

```text
apps/                          # 进程入口、参数和依赖组装
  engine/  desktop/  cli/
modules/
  foundation/                 # ID、单位、错误、时间/预算、只读缓冲
  contracts/                  # 版本化操作/查询/事件/资源/显示契约
  document/                   # 实体目录、实体表、ReadView、EditSession、引用索引
    geometry/  mesh/  physics/  organization/
  application/                # Session、OperationRegistry、CommitCoordinator、Lifecycle
  history/                    # ChangeSet应用/反向应用、游标、保存点
  query/                      # 查询、选择、空间/归属索引
  runtime/                    # 任务状态、执行器端口、事件、资源预算
  artifacts/                  # 资源身份、冻结来源、暂存/发布清单
  visualization/              # 只读RenderPacket契约对应的投影生产逻辑
  clients/                    # 公共SDK、连接/重连/事件/资源读取
features/                     # 按功能纵向组织，handler不直接写库
  project/  organization/  materials/
  geometry/  mesh/  analysis/
profiles/
  nastran/                    # 能力清单、字段/规则、卡片映射与解析
adapters/
  storage_sqlite/  transport_local/  executor_local/
  geometry_backend/  meshing_backend/  rendering_vtk/
ui/
  desktop/                    # Shell、Workspace、ViewModels、Editors、feature contributions
schemas/                      # 权威实体/操作/记录格式定义
scenarios/
  beam_workflow/              # 组装公共操作，不成为另一份模型或私有写路径
tests/
  unit/  contracts/  integration/  architecture/  fixtures/  extension/
tools/                        # 契约生成、脚手架、依赖/格式/兼容检查
```

首批真实编译边界建议为foundation、contracts、document、application/history/runtime、query/render-data、具体适配器、client SDK、desktop UI。业务体量尚小时可以合并application内部子目录；核心与第三方库、服务端与客户端等关键边界必须是可检查的构建边界。

依赖方向固定如下：foundation无产品框架依赖；contracts只依赖foundation；document依赖foundation；application依赖document、contracts及其端口；功能handler依赖document和应用扩展契约，通过宿主静态注册；具体适配器在宿主组装。clients和desktop只依赖contracts、客户端传输及显示消费者，不依赖document/application。

schema生成的领域记录与传输DTO分属不同目标。两者可来自同一权威定义，但转换发生在服务边缘；不能因“共享类型”让GUI链接整个领域库。静态注册清单的增项是允许的扩展位置，通用分发算法保持不变。

每个模块仅维护一份短说明：负责什么、公开接口、依赖谁、哪些层禁止依赖、最小示例和测试命令。CI/CMake检查依赖清单与实际构建目标一致，检测客户端偷链领域实现、核心包含Qt/SQLite/VTK、循环依赖和跨模块包含私有头。设计图不再作为依赖隔离的唯一证据。

## 4. 实体目录与文档层

### 4.1 一份权威定义，保留强类型

建议使用小型声明式schema生成普通C++记录类型及EntityTraits。权威定义包含稳定的类型/字段编号、字段类型、单位、默认/可选语义、引用目标及记录版本；业务代码使用生成的强类型结构，不直接编辑字典。

生成范围限定为机械工作：类型声明、字段访问、引用枚举、记录编码/解码、基本协议转换和字段描述。物理有效性、复杂引用规则、CAD操作和Nastran映射仍写成显式C++规则。

C++20没有自动字段反射。若决定采用手写类型＋显式traits，也必须承认字段声明与traits的同步成本，并用覆盖测试检查。不能仅增加一个Registry类就宣称消除了重复维护。

类型编号、字段编号和迁移规则不可依赖容器顺序、类名或注册先后；删除字段保留编号，未知未来版本不能进入可编辑状态。

### 4.2 ReadView、EditSession与ChangeSet

`ReadView`提供带版本的不可变读取；功能模块不能取得整个文档的可写引用。`EditSession`记录本次实际触及的实体/关联/网格块，生成：

```text
PreparedChange
  document + epoch + base revision
  normalized command + frozen target profile
  ChangeSet[(record kind, stable key, before, after)]
  reference/index updates
  ChangeImpact + resource estimate
```

通用事务协调器负责版本、调用者、幂等、配额、持久化和发布；handler负责领域语义。历史反向应用ChangeSet，SQLite只接收已经准备好的提交批次。稳定EntityId和记录键是事实身份，数组位置只是存储实现细节。

R2先使用实体表、稳定记录键和共享只读容器，证明扩展隔离；R4再将普通提交切换到记录/块批次，并对节点坐标、连接等密集数据实现所需的固定大小块。最终至少有一条局部修改只复制/提交局部记录或块的真实路径。接口解耦与性能改造分别验收，避免把两项大改动混成一个步骤。

### 4.3 几何、网格和组织从此处分开

- GeometryDocument/GeometryEntity：平台几何身份、后端资源/修订、拓扑映射和建模操作的来源；不能把第三方临时face/edge序号直接当永久EntityId。
- Mesh：独立MeshId、节点/单元集合、坐标和连接数据，以及导入/手工/几何派生的来源。Part是组织归属，不能替代Mesh。
- GeometryMeshBinding：几何修订、网格实体与几何支撑实体的关联；几何变化后明确标记仍有效/需重建，局部重网格需返回旧新实体映射。
- AnalysisScope：明确引用网格/实体范围，避免永远默认所有分析使用整份全局Model。
- Display tessellation：可重建显示数据，具有真实实体反向映射，不成为FE物理网格。

先做直线/一维网格所需的最小字段，并用真实数据保存/恢复这些关联。通用CAD拓扑命名与复杂重网格仍须在接入对应后端时解决，不能靠声明接口宣布已经完成。

## 5. 操作、功能包与客户端

一项操作的注册项同时包含名称/版本、类型化输入输出、单位/字段约束、执行类别、目标上下文、能力条件、handler、可选UI呈现提示。能力发现从实际注册且满足条件的项生成，消除手写`supported()`与另一份路由名单。

操作按生命周期写、模型写、查询、视图会话、后台任务区分；不把保存、相机或选择错误地塞进模型undo。图形/本地运行能力缺失时显式不可用。

处理链统一为：

```mermaid
flowchart LR
    Entry[GUI / CLI / 外部AI桥] --> SDK[公共SDK与类型契约]
    SDK --> Router[操作注册与分发]
    Router --> Handler[功能handler]
    Handler --> Plan[PreparedChange / TaskPlan / QueryResult]
    Plan --> Commit[统一提交协调器]
    Commit --> Store[存储批次事务]
    Store --> Publish[发布ReadView与变更事件]
    Publish --> View[查询 / RenderPacket / 客户端刷新]
```

同步模型操作和后台任务产生的候选通过相同协调器提交。新增handler无需修改通用提交逻辑。复杂界面可以有专用编辑器，但不能在Qt层重新定义物理合法性。

客户端SDK集中处理协议编码、请求关联、超时/幂等查询、重连、事件序号和资源读取。GUI、CLI复用同一协议定义；未来MCP桥可用不同语言生成同一契约，不要求强行链接同一个C++库。

桌面窗口只负责布局、命令入口和ViewModel连接。工程、模型树、属性、视图、任务与问题面板分别有控制器；名称、类型、字段展示来自元数据，专用渲染/编辑器通过明确注册加入。

## 6. 运行、存储和显示链路的最小真实实现

### 后台任务提前进入骨架

以一维网格生成或导入作为真实任务，落实queued/running/cancel_requested/committing/terminal状态、进度、取消令牌、任务预算、输入版本、失败诊断和重启后的中断标记。提交前取消不发布候选；提交后的取消不能伪称撤销已提交模型。

首版可限制并发，采用本地线程/进程执行器。关闭带运行任务的文档须明确拒绝或取消并等待终态；不为完成简单场景立即建设分布式调度或多个退休工作库。

### 存储不再只有整份payload接口

保留工作库、明确工程快照及save intent的语义。新增PreparedCommit批次，原子包含脏记录/块、历史游标、修订、幂等事实和关联任务状态。SQLite仍不承担领域规则，改动实体字段不应新增一段SQLite专用业务代码。

旧工作库/工程提供读入迁移到新副本的路径和夹具；损坏、未知类型或不兼容profile不静默填空。正常保存完整快照可以保留，但一项普通局部编辑不应总是重新编码整份模型。

### 资源、事件与渲染

- 控制消息保留小型结构化数据；大网格用带DocId/Epoch/Revision的只读资源描述及有界分块通道。
- 事件包含序号和版本，客户端发现缺口/重连时重新查询；轮询可作为回退机制。
- 渲染按mesh/block组织并支持局部更新，避免每次材料或节点修改重新发送整份场景。
- RenderPacket使用明确的点/线/面等显示基元及真实实体映射，物理拓扑到显示基元的映射归投影层。

无需现在证明亿级性能，但需要用“只改一个对象”验证数据复制、持久化和传输没有结构性地绑定全模型大小。

## 7. 求解器包和版本策略

先把Nastran从“特殊入口分支”迁入一个真实静态能力包。包提供支持矩阵、映射、字段约束及适配器，平台只解析目标绑定与通用契约。当前严格梁子集可继续保留，新增其他卡片另行实现。

Profile的语义版本/定义摘要与实现构建指纹应分开。当前摘要直接散列源码文件，目录移动或格式变化也会使既有工程的引用改变。重构时需要稳定的语义声明、明确规则版本和兼容策略；构建指纹保留追溯。实际语义变更必须升级规则或迁移，不能仅凭声明“兼容”继续解释旧模型。

不承诺新增物理过程只替换一个模板。新拓扑、材料行为和求解控制的领域变化仍由强类型对象、能力规则和测试明确表达。

## 8. 骨架验收场景与扩展验收

建议主场景为：

**简单直线几何/基准线 → 一维网格任务 → 材料/截面与基本载荷约束 → 组织/查询/选择 → 局部编辑 → undo/redo → 保存/关闭/恢复 → 显示 → 检查与Nastran产物发布。**

主场景先采用平台内置的解析直线和确定性均匀一维离散器：输入端点及分段数，真实生成GeometryId/MeshId、节点/梁及来源关联，并经过任务、取消和保存恢复。它实现P0原本需要的直接梁建模，范围只到解析直线，不自研通用CAD/网格内核，也不声明外部引擎已经接入。后续外部开源引擎通过相同适配合同接入，通用CAD拓扑命名另行真实验证。真实求解器与真实AI调用可继续在M4/M5验收，但其端口、生命周期归属及契约边界须在骨架中明确。

除主场景，必须完成以下小型扩展练习。记录变更文件及是否触碰通用层；注册清单和生成文件变化不等于修改通用算法。

| 验收 | 实际扩展 | 必须证明 |
|---|---|---|
| EXT-01 字段 | 为一个现有实体增加可选字段 | 表单/接口、编辑、历史、保存恢复及旧schema夹具通过；不修改事务、历史算法、SQLite事务和传输 |
| EXT-02 命令 | 新增批量节点平移 | handler＋操作定义＋测试＋必要UI入口即可；单位、引用/范围、旧版本、重试和取消有证据；通用分发和生命周期代码不变 |
| EXT-03 拓扑 | 增加Tri3网格拓扑及显示 | 连接/归属/引用、拾取、历史和存储贯通；仅在类型/拓扑定义、功能/投影与对应适配器扩展；未实现的壳分析/导出仍不可用 |
| EXT-04 适配 | 内存/SQLite或测试执行器切换 | 同一套核心合同测试复用，入口不分叉出另一套业务模型 |
| EXT-05 代价 | 大样本内只修改一个节点/材料 | 记录触及记录/块、写入字节和传输字节；不会因整个文档实体数增加而无条件复制/写出全部状态 |

EXT-03是扩展机制验证，不把完整壳单元分析纳入主场景。EXT-05使用1000、10000、100000节点的链状模型，选择固定度数的内部节点，记录一次移动触及的逻辑记录、脏块、复制/编码/写入/传输字节。首次加载和明确保存完整快照允许全量工作；普通局部编辑的数据复制/持久化/传输量应受固定块大小和实际影响范围限制，而非无条件随全模型同比增长。校验扫描和索引重建耗时另行报告，不以该测试宣称所有操作达到常数复杂度或亿级性能。全链测试的数量只作为回归入口，不能代替上述修改边界证据。

## 9. 面向后续AI辅助开发的任务组织

每个功能包提供短的任务契约：目标及非目标、可修改目录、公开输入输出、单位/引用/版本约束、样例、必须执行的定向测试。脚手架从现有模式生成操作声明、handler入口、测试样板和可选UI贡献项，避免模型自行发明接口。

功能扩展任务默认禁止修改提交协调器、存储协议、公共schema版本策略和跨模块依赖；确实需要变更时单列架构任务。自动检查“禁止触碰区域”是审查辅助，不能取代人工判断。

模块测试标签、快速构建目标、旧文件夹具、错误诊断规范和一个完整参考功能包，是降低后续上下文和返工成本的主要工具。所有模块仍保留人工可读代码；生成代码可复现但不手改。
