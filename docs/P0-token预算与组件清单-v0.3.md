# 本地 P0：token 预算与现成组件清单 v0.3

> 历史讨论：本文件保留当时的分析与估算；当前开发依据为 [设计基线1.0](baseline/README.md)。冲突时不沿用本文件旧范围。

日期：2026-09-25。依据：[P0 可行性分析](P0本地平台可行性分析-v0.2.md)。本次仅更新估算和建议清单，没有安装依赖或开始实现。

## 1. 结论

完整本地 P0 建议按 **350万—700万累计输入/输出 token** 预留；可用 **500万** 作为规划中心值。它们是缺少实际项目开发数据时的工程估算，置信度低，不是已测消耗、执行上限、工期或完成保证。

建议产品主要直接依赖先采用 **Qt Widgets + VTK + SQLite**；核心语言建议 C++，保持领域/应用服务与 UI、显示、存储适配器分离。开发验证采用 Catch2、Qt Test、pyNastran，构建采用 CMake/CTest。几何网格引擎保留在候选清单中，实际出现 CAD/重网格用例时再接入。

桌面客户端与 C++ 是本轮预算参考路线，尚不表示用户已经冻结语言和客户端。若选择浏览器或强制独立进程，应重新估算相关部分。

## 2. 估算口径与假设

预算覆盖从当前无产品代码状态到 P0 验收的后续 AI 辅助工作，不回算此前已经消耗的 token。

计量方式：各次模型调用的输入与输出 token 累加；重复上下文、子代理输入输出、修复与审查都计入。缓存输入可单独记录但仍属于总输入。工具返回文本在被模型读取时进入输入；运行本地编译/测试的 CPU 时间不等于 token。

不同模型的有效产出、上下文管理与缓存策略会影响实际消耗或费用，所以此数不能直接换算成价格、订阅额度或开发工时。

估算假设如下，未确认项必须在实施时核对：

- 单一桌面客户端、单一首发操作系统，本地运行，逻辑前后端分离。
- 中小模型完成闭环，不含亿级性能保证和远程服务器实现；具体数量/硬件仍待定。
- P0 装配为层级组织；不把重复实例与复杂变换语义默认计入。
- 一个 Nastran 方言、受控卡片子集、一维线性静力悬臂梁；已有可用求解器供验收。
- 完整保留用户列出的多视角模型组织、可组合查询、框选/隐藏/穿透/反选、引用依赖、工程/BDF IO、undo/redo、基础检查、任务取消/版本/配额/恢复。
- 恢复已保存及已持久化状态，识别中断任务；不默认所有算法断点续算或无限跨重启历史。
- P1 脚本只在 P0 建立可调用接口；其余未列功能不设计。
- 采用成熟库、有限卡片实现和有代表性的真实样本；不假定一次编写即通过验收。

## 3. 自下而上的预算

单位：万 token。各行是增量分工；本模块基本测试包含在对应行中，最后一行承担跨模块和实际求解验收，避免重复计数。

| 工作包 | 区间 | 覆盖内容 |
|---|---:|---|
| 规格、接口及依赖集成 | 15—30 | 固定范围、接口契约、构建骨架、Qt/VTK 兼容性验证 |
| 文档模型与组织关系 | 40—80 | 稳定 ID、装配/部件/集合/INCLUDE、材料属性、引用与基础检查 |
| 命令、undo/redo 与恢复 | 50—100 | 原子修改、差量、保存点、持久化历史边界、恢复故障测试 |
| 任务与生命周期 | 25—50 | 后台队列、取消/提交竞争、版本冲突、资源计量、状态恢复 |
| 工程与最小 Nastran 读写 | 30—60 | 工程格式、保存/另存、限定卡片、INCLUDE 与格式错误诊断 |
| 查询与精确选择 | 30—70 | 条件组合、集合运算、空间/可见性选择、实体映射与一致性 |
| 基础界面与 VTK 接入 | 30—60 | 必要工作区、多视角树、最小属性表单、显隐高亮与联动 |
| 实际求解、集成验收与打包 | 35—70 | 悬臂梁数值核验、完整回归、中小模型性能、部署与诊断 |
| **基本工作合计** | **255—520** | |
| **约 30% 风险预留** | **76.5—156** | 接口假设修正、难复现错误、依赖/驱动差异等 |
| **计算结果** | **331.5—676** | |
| **向上取整后的规划区间** | **350—700** | 规划中心值 500 |

该区间是工作分解后的判断，不是从之前服务器方案按百分比扣减得出。与前期 1200万—5000万占位预算相比，交付对象已经改变，不能拿两者计算精确“提效百分比”。

### 分阶段控制

可先拿 **80万—120万** 作为第一阶段的检查点预算，目标是构建可用、文档模型基本成立，并打通一条无界面的修改—撤销—保存—重开回路。它不是全部底层或全部 P0 的交付承诺。

记录各工作包实际模型用量、完成的验收场景、返工原因和剩余缺陷；在该检查点重估，而不是一次性把完整区间视为固定消耗。

达到 500万或接近 700万也不自动代表任务完成；验收结果决定完成状态。这里没有设置自动执行预算或启动持续开发。

## 4. P0 推荐直接运行依赖

| 组件 | 用途 | 边界 | 公开许可概况 |
|---|---|---|---|
| Qt 6 Widgets / Core / Gui，以及所需图形集成模块 | 窗口、菜单、快捷键、树表、属性表单、文件对话框、设置 | Qt Model/View 适配业务查询；不让 QWidget/QObject 成为每个 FE 实体的核心结构 | 按模块 LGPL/GPL/商业许可，采用时核对具体模块 |
| VTK | 相机、网格显示、拾取、框选辅助、空间查询与高亮的基础设施 | 派生显示数据由适配器管理；条件选择、反选范围和实体身份由平台定义 | BSD-3-Clause |
| SQLite | 工程元数据、关系、版本记录、历史持久化、工程快照/备份 | 内存模型独立；数据库事务不等于用户 undo 或完整会话恢复 | 核心代码公共领域 |

Qt 原生 QDockWidget 已支持停靠与浮动，因此必要工作区先复用它，暂不加 ADS。[QDockWidget](https://doc.qt.io/qt-6/qdockwidget.html)、[Model/View](https://doc.qt.io/qt-6/model-view-programming.html)、[Qt 许可](https://doc.qt.io/qt-6/licensing.html)

VTK 已提供科学显示、拾取和 Qt 集成能力，避免自建完整渲染与拾取基础设施。[VTK 官方功能及许可](https://vtk.org/about/)

SQLite 可以减少数据库可靠写入和快照的开发量，但它的数据库日志不会自动变成用户操作历史。数据库外的 BDF 文件也不受同一个数据库事务自动保护。[SQLite 简介](https://sqlite.org/about.html)、[原子提交](https://sqlite.org/atomiccommit.html)、[备份 API](https://sqlite.org/backup.html)、[许可](https://sqlite.org/copyright.html)

“三个直接依赖”指主要产品依赖的控制目标，不表示只有三个实际库文件；Qt/VTK 构建仍会有传递依赖。实施时固定兼容版本组合和所需模块，不直接追逐每个库的最新版本。

## 5. SQLite 与核心数据的建议分工

工程结构、属性、关系、历史适合持久化到 SQLite；节点/连接等批量数组可评估分块 BLOB。P0 不要求同时引入 HDF5 与多套存储。

运行时查询、显示和编辑使用核心的数据结构与索引，避免逐单元执行 SQL 或每帧查询数据库。内存表示与数据库 schema 通过存储适配器转换。

是否采用分块 BLOB、具体块大小、事务配置、工作副本与保存点机制，在最早的代表性数据原型中验证。另存采用数据库一致性快照路径，不能随意复制正在写入的主数据库文件。上述是选型方向，不是已经验证的格式设计。

## 6. 开发、验证与构建工具

| 工具 | 用途 | 是否随产品运行 |
|---|---|---|
| Catch2 | 文档、引用、查询、事务、读写与恢复回归 | 不必；测试程序依赖 |
| Qt Test | 必要的 Qt 交互和界面适配测试 | 不必；复用 Qt 测试能力 |
| pyNastran | 样本生成、BDF 读写对照、支持子集的交叉检查 | 默认不随产品发布 |
| CMake / CTest | 构建、依赖接入与测试执行 | 构建工具 |
| 指定已有 Nastran 求解器 | 悬臂梁真实运行及位移/反力核验 | 外部验收依赖，是否随用户环境提供待定 |

Catch2 为 Boost Software License 1.0；pyNastran 为 BSD-3-Clause；CMake 为 BSD-3-Clause。Qt Test 按实际模块许可核对。[Catch2](https://github.com/catchorg/Catch2)、[Catch2 许可](https://raw.githubusercontent.com/catchorg/Catch2/devel/LICENSE.txt)、[pyNastran 许可](https://github.com/SteveDoyle2/pyNastran/blob/main/LICENSE.md)、[CMake 许可](https://cmake.org/licensing/)

pyNastran 很适合减少格式学习与样本制作成本。产品端建议仅实现已确定子集的 C++ 读写适配，不自写完整 Nastran 生态；固定/自由/大字段和续行等也应按实际子集明确支持。若实际格式范围增长，应重新比较嵌入或独立 Python 工具进程与 C++ 子集实现的总成本。pyNastran 验证通过不能代替指定求解器实际接受并得到正确结果。

标准 C++ 容器、线程和合作式取消机制优先复用。小型任务队列、进度、版本和提交语义仍由平台实现；先不引入大型任务图框架。标准取消机制不能强制打断任意第三方算法。

## 7. 暂不接入的组件

| 组件 | 本次处置及触发条件 |
|---|---|
| OCCT | 保留为首选几何候选。P0 梁网格若直接创建/导入，无需 CAD 核；首次需要 STEP/IGES、几何修复或 BRep 操作时接入 |
| Netgen / Gmsh | 保留候选；首次需要自动划分或局部重网格时，按算法类型和许可二选一评估 |
| ParaView / trame | 远程与服务器路线后置，P0 不引入其平台/远程显示框架；VTK 单独使用 |
| Qt ADS | 原生停靠满足必要工作区时暂缓 |
| HDF5 | SQLite/块数据原型出现明确存储瓶颈，或后续容量需求到来时再评估 |
| CGAL / SMESH | 当前无必须由它们承担的已确定算法，不增加平台依赖 |
| Python 绑定/插件框架 | P0 建立可调用接口；P1 需要脚本运行时再选择具体绑定方式 |

这是推迟接入，不是改成自研几何或网格算法。未来接入仍遵循原先使用成熟开源引擎的方向。本轮不设计这些未来功能。

## 8. 必须由平台拥有的能力

现成组件之外，保留以下自主实现：实体与组织关系、引用语义、查询选择的组合和候选范围、命令/原子提交、undo/redo 差量、任务状态和恢复策略、限定 Nastran 业务与校验。

显示拾取可复用 VTK，数据落盘事务可复用 SQLite，界面结构可复用 Qt；业务层统一协调它们，不重写通用基础设施，也不让第三方对象占据核心公共接口。

## 9. 哪些变化需要重估

- 从单一首发平台变成多个平台同时验收，或改为浏览器+独立本地服务。
- 从限定 Nastran 子集变成任意真实工程 BDF 的兼容编辑。
- 强制多实例装配、任意跨重启撤销、任务断点续算。
- 悬臂梁改为需要 CAD/网格生成的壳/实体路线。
- 当前“中小模型”确定为明显更大的数量级，或要求更严格低延迟。

这些变化目前没有计入，不能用风险预留默默吞入新范围。第一阶段应记录真实用量后更新本文，许可证也需随最终锁定的版本和构建依赖核验。
