> 历史讨论：本文件保留当时的分析与估算；当前开发依据为 [设计基线1.0](baseline/README.md)。冲突时不沿用本文件旧范围。

> 范围更新：用户已将 P0 改为本地中小模型、底层能力优先，服务器/亿级实现后置。本文旧路线与预算仅作历史研究记录；当前依据见 [P0 本地平台可行性分析](P0本地平台可行性分析-v0.2.md)。

日期：2026-09-25。状态：需求分析草案，尚未冻结需求或进入实现。组件能力依据官方文档；技术取舍、性能指标和 token 数量为本项目的建议或估算，不是已经验证的结果。

## 1. 产品定位与已确认需求

目标是自主开发面向大规模有限元模型的 CAE 前处理平台，复用成熟开源几何、网格及必要的平台组件。

用户已确认：

- 规模目标为“亿级网格”；节点数、单元数或二者合计的口径仍待确认。
- 核心场景是**导入既有亿级模型，流畅查看、选择、分组，并做局部修改**。
- 单一 Nastran 模板；具体方言、版本、分析类型和卡片范围尚未确定。
- 只保留必要的几何、网格功能，平台功能相对完整。
- 界面流畅优先，支持 undo/redo。
- 已确认接受操作时简化显示、停止后渐进细化；局部编辑及最终选择必须准确。
- 部署已确认：普通电脑作为客户端，大模型在服务器处理；桌面客户端或浏览器先比较成本与交互效果，再决定，不预先冻结。
- 本轮工作是需求分析、开源组件预研和粗略 token 预算。

由此建议的主流程：打开 BDF/工程 → 获取结构与粗预览 → 后台建立索引 → 浏览/定位/筛选 → 隔离局部工作区 → 编辑与检查 → 撤销/重做 → 保存工程 → 校验并导出 Nastran。

这一定义把首轮难点集中在数据与交互，不要求首轮证明从复杂工业 CAD 生成亿级网格。必要的局部网格生成仍可纳入后续功能。

## 2. 首版功能边界建议

以下优先级为建议，不表示用户已经逐项批准。

| 领域 | 首版必须形成的闭环 | 可后置或按需引入 |
|---|---|---|
| 工程与文件 | 新建/打开/保存/另存为，版本识别，最近工程，自动恢复；工程文件与 BDF 交换格式分离 | 远程工程库、多人实时协同 |
| Nastran 数据 | 分阶段导入、导出、INCLUDE 组织、ID/引用校验、错误定位；保留未知数据的明确策略 | 全部卡片、全部分析序列、多求解器 |
| 模型组织 | 部件/属性/材料/集合树、搜索过滤、集合管理、可见性和颜色、隔离/恢复 | 企业级物料和流程管理 |
| 选择与查询 | 点选/框选/区域选、实体类型过滤、按 ID/属性/质量筛选、穿透与可见选择、选择集；清楚区分预览与最终结果 | 高级自动特征识别 |
| 属性与编辑 | 属性面板、表格批量编辑、材料/属性分配、局部移动/删除/复制、基本连接修复 | 任意大范围重拓扑或全量重网格 |
| 分析准备 | 选定 Nastran 卡片集内的材料、截面/厚度、坐标系、载荷、约束、工况与引用管理 | 求解器开发、完整后处理 |
| 可视化 | 旋转/缩放/平移、标准视图、裁切、局部隔离、清晰高亮、基本测量、载荷/约束符号 | 默认开启高成本写实材质和全场透明 |
| 几何 | 按实际输入确定 STEP/IGES 支持；测量、定位、有限修复、必要裁剪/分割 | 完整参数化 CAD、复杂特征树 |
| 网格 | 质量检查、孤立/重复检查、局部节点与单元修正；必要时局部重网格 | 自动中面抽取、工业级全六面体、多种高端网格算法 |
| 平台体验 | 停靠布局与恢复、快捷键、命令搜索、日志与诊断、进度与取消、偏好设置、高 DPI、统一 undo/redo | 插件市场、复杂脚本 IDE |

“必要几何/网格”必须最终列为可验收的操作清单。尤其是中面抽取、薄壁四边形网格、复杂接触自动生成，不能因称为“基本功能”而默认低成本。

## 3. 亿级需求的真实约束

### 3.1 需要区分的规模

- 存储规模：节点、单元、属性和引用的总量。
- 显示规模：当前需要提交给 GPU 的点、线、三角形和符号。
- 查询规模：一次选择或过滤需要遍历的范围。
- 修改规模：一次事务修改的实体数、字段数和依赖关系。
- 历史规模：可撤销变更的累计字节数。

亿级模型可浏览，不自动意味着所有边线、标签、内部单元同时可见，也不意味着全量编辑可以瞬间完成。实体体网格的外表面可能远小于总单元数；壳模型、断开的零件、裁切和透明显示会显著改变成本。

建议把显示降级与数据精度分开：模型始终保留精确数据；浏览阶段可使用显示代理、分块和 LOD；编辑与最终选择必须映射回真实实体 ID。用户已确认接受这一显示策略；具体显示预算和细化延迟仍待硬件基准确定。

### 3.2 内存数量级示例

仅用于说明下限，假设 **1 亿节点 + 1 亿四节点四面体**，坐标 float64、节点/单元/属性 ID 与连接索引均按 64 位计算，十进制 GB：

| 数据 | 算式 | 大小 |
|---|---|---:|
| 节点坐标 | 1e8 × 3 × 8 B | 2.4 GB |
| 节点 ID | 1e8 × 8 B | 0.8 GB |
| 四面体连接 | 1e8 × 4 × 8 B | 3.2 GB |
| 单元 ID | 1e8 × 8 B | 0.8 GB |
| 单元属性 ID | 1e8 × 8 B | 0.8 GB |
| 上述原始数组合计 | | 8.0 GB |

这还不包含坐标系字段、混合单元偏移、反向邻接、空间索引、源文件记录、表面提取、显示缓存、GPU 副本、算法临时区和撤销历史。八节点六面体的连接数组在同样假设下为 6.4 GB。每节点/单元再加 100 B 的对象和管理开销，2 亿实体就会再增加 20 GB。

内部使用 64 位容量和稳定 ID，并不代表目标 Nastran 求解器接受任意 64 位外部编号；导出限制必须按选定方言验证。密集内部索引与外部稀疏 ID 应分离，不能按最大外部 ID 分配数组。

不能据上述下限直接认定 16/32/64 GB 机器足够，也不能先承诺 128 GB 必然达标。硬件和真实模型分布确定后才有性能合同。

## 4. 流畅度与正确性的首轮验收建议

数值均为待基准验证的目标，不是现成组件承诺。必须固定硬件、分辨率、模型、视角、显示模式和缓存状态。

| 行为 | 建议测量或目标 |
|---|---|
| UI 输入响应 | 常用操作反馈 P95 ≤100 ms；后台导入、检查和保存期间仍可操作界面 |
| 连续旋转/缩放 | 允许降级显示时，以帧时间 P95 ≤33 ms（约 30 FPS）为首轮目标，另记录 P99 卡顿 |
| 局部精细编辑 | 活跃工作区有明确实体上限；精细显示、准确选择与编辑独立验收 |
| 点选 | 已加载工作区 P95 ≤200 ms；反馈实体类型和真实 ID；未加载细节时不得把近似结果当精确结果 |
| 大集合过滤/质量检查 | 后台执行，可见进度与取消；记录吞吐和峰值内存，不强求全量操作瞬时完成 |
| 打开工程 | 分别记录首次结构可用、粗预览可用、索引完成时间；冷启动与缓存重开分别测试 |
| 内存与显存 | 指定 RAM/VRAM/磁盘历史配额；预估超限、按需换入换出，禁止无提示持续增长 |
| 正确性 | 导入/导出语义往返一致；未知数据策略明确；取消不产生半提交；undo/redo 后引用一致 |

建议最早建立三类数据基准：大壳模型、大实体模型、多部件混合模型。规模按百万、千万、亿级增长，同时变化可见表面数和单次修改比例。合成数据验证容量，真实模型验证格式与工程操作，不能互相替代。

### 4.1 客户端—服务器带来的新增需求

服务器处理大模型已经确认，但这并不自动等于服务器渲染。鉴于普通电脑和亿级整体浏览目标，建议以服务器渲染作为全局视图的第一原型，客户端主要接收图像与交互状态；局部精细区域是否下载显示数据，作为后续混合方案验证。

- 服务端保存权威模型、空间索引、事务历史与工程文件；客户端不持有亿级实体全集。
- 远程显示分别测量服务器帧时间、图像传输吞吐和输入到画面更新的端到端延迟。服务器达到 30 FPS，并不代表用户操作低延迟。
- 网络验收需指定 RTT、带宽、抖动、分辨率；局域网、园区网络与公网不能共用一个流畅度结论。
- 选择请求携带视图/相机状态、画面对应模型版本；由服务端准确求交并返回稳定实体 ID，防止旧画面误选新模型。
- 修改请求需要事务 ID 和版本校验；断线重试不能重复执行删除、移动等操作；重连后同步已提交状态。
- 大型文件支持服务器侧路径或断点续传，避免每次打开都从普通客户端重新上传。
- 至少提供项目访问、会话隔离、任务与资源配额；远程访问不自动意味着支持多人同时编辑一个模型。建议首版采用单文档单写者，待确认。
- 先以单台高内存/GPU 服务器证明业务闭环，跨节点分布式计算是否必要由基准决定；若单机容量不足再扩展。

[ParaView](https://docs.paraview.org/en/latest/ReferenceManual/parallelDataVisualization.html) 已有远程/并行渲染与图像回传机制；[trame](https://kitware.github.io/trame/guide/tutorial/vtk.html) 提供本地和远程显示接入，适合快速验证浏览器端交互。两者可减少显示基础设施工作，但不直接提供本产品的 Nastran 编辑事务。

## 5. Undo/redo 是文档事务能力

建议所有会修改模型的 UI 命令、表格批量操作、脚本和第三方算法，最终通过服务端同一个事务入口提交。客户端的 undo/redo 菜单只反映服务端历史，不能形成另一份权威编辑栈。

- 小修改：记录字段差量；连续拖动或连续输入可以合并。
- 大修改：按块记录旧/新内容或引用不可变块，历史允许落盘；不复制完整工程。
- 删除/重网格：同时记录关联、属性、分组和引用变化；仅恢复坐标不足以保证正确性。
- 异步任务：基于明确的模型版本计算；提交时检查冲突。撤销不能和未完成的提交互相穿插。
- 取消/失败：未提交结果可以丢弃；已提交动作必须原子地恢复。
- 配额：按历史字节数和磁盘容量管理，而不只按“撤销 100 步”。保存点、历史裁剪、重启后是否恢复历史均需定义。
- 相机、选择和模型编辑是否共用历史尚待确认；建议模型历史独立，导航提供单独的返回能力。

举例：若一次修改 1 亿节点坐标，单份双精度旧坐标已有 2.4 GB，若同时保存前后坐标则为 4.8 GB，尚不包含索引和日志。因而“支持 undo”需要定义最大事务，而不是只增加一个按钮。

[Qt Undo Framework](https://doc.qt.io/qt-6/qundostack.html) 提供命令、合并、宏、保存状态和操作入口，但其命令数限制不是历史字节预算。OCCT 的 [OCAF](https://occt3d.com/dev/doc/overview/html/occt_user_guides__ocaf.html) 有几何文档事务能力，仍需与平台的网格/Nastran 事务统一协调。

## 6. 优先评估的开源组件

许可栏仅记录上游公开许可。实际采用前按选定版本、模块、传递依赖和发布方式复核；本轮不把“开源”解释为可无条件采用。

| 组件 | 可缩短的工作 | 使用边界与结论 | 上游许可概况 |
|---|---|---|---|
| Qt Widgets | 菜单、快捷键、树表、属性编辑、对话框、桌面交互 | 若选择桌面客户端则为外壳优先候选；树表按需加载，不能为亿级实体创建 UI 对象 | Qt 按模块为 LGPLv3/GPL/商业授权等 |
| Qt Advanced Docking System | 停靠、浮动、自动隐藏、工作区布局保存 | 若原生 QDockWidget 不足则引入；验证跨窗口视口和高 DPI | LGPL-2.1 |
| trame | Web UI、状态同步、VTK/ParaView 远程视口接入 | 优先用于远程交互原型；状态同步不能代替可靠编辑事务 | Apache-2.0 |
| vtk.js | 浏览器局部显示、轻量几何预览、远程视口辅助 | 浏览器路线的条件候选；普通客户端不接收全量亿级数据 | BSD-3-Clause |
| VTK | 裁切、选择、标量着色、科学可视化与 Qt 集成 | 服务端第一显示基线；通过适配层接入，不能把默认数据管线当亿级性能保证 | BSD-3-Clause |
| OCCT | CAD 导入、BRep、有限修复、布尔、离散化 | 优先作为几何服务；不要用 CAD 拓扑对象逐个表达 FE 单元 | LGPL-2.1 + special exception |
| Netgen | 自动表面/四面体网格与优化 | 若必要功能以四面体为主则优先试验；壳/四边形需求要另评估 | LGPL-2.1 |

| HDF5 / SQLite | 分块大数组 / 工程元数据与事务存储 | 数据持久化候选；HDF5 分块不等于跨资源事务，SQLite 不应逐实体承担渲染热路径 | 采用时核验具体发行包 |

### 条件引入，而不是一开始全部叠加

- **ParaView**：在已确认的服务器路线中升级为高优先级远程显示基线；其并行显示、LOD、交互/静止质量切换可减少基础设施开发。完整平台的数据流和代理体系与可编辑 Nastran 文档并不相同，直接套壳是否省时要证明。[官方说明](https://docs.paraview.org/en/latest/ReferenceManual/parallelDataVisualization.html)
- **SALOME SMESH**：分组、过滤、质量检查和网格编辑丰富；官方高级接口与 SALOME Study/CORBA 存在耦合。可以评估独立算法层，不把整套平台默认当低成本依赖。部分商业插件并非开源算法。[仓库](https://github.com/SalomePlatform/smesh)、[接口文档](https://docs.salome-platform.org/latest/gui/SMESH/smesh_module.html)
- **CGAL**：适合特定几何算法缺口；按包选择，不能把整个项目都当作 LGPL。[逐包目录](https://doc.cgal.org/latest/Manual/packages.html)、[许可说明](https://www.cgal.org/license.html)
- **Qt Quick**：欢迎页和少量动态面板可评估，不因视觉现代就全面替换复杂桌面控件。混用 QQuickWidget 存在额外离屏绘制和渲染循环限制。[官方性能说明](https://doc.qt.io/qt-6/qquickwidget.html)
- **OCCT AIS/MeshVS**：适合几何预览和拓扑选择，是显示路线备选；是否承载亿级 FE 要实测。[MeshVS](https://dev.opencascade.org/doc/refman/html/package_meshvs.html)

Gmsh 官网对闭源分发集成说明了商业许可要求；单纯改为独立进程不能在本轮据此得出授权已解决的结论。若未来明确闭源商业发布，授权边界应成为选型输入。

本轮没有获得任何候选组件在目标机器、目标 Nastran 模型和完整交互流程上满足亿级需求的证据。并行网格算法的生成吞吐不能替代平台交互基准。

## 7. “不影响其他模块实现”的可验收解释

建议将其具体化为：

1. 平台拥有模型实体、稳定 ID、Nastran 语义、分组、工程格式和全局事务；组件内部对象不直接成为 UI/文件接口。
2. 第三方网格算法接收限定范围输入，输出候选变更；成功后由平台统一提交，可撤销。
3. 显示组件只持有可重建的显示数据；替换显示组件不修改工程语义。
4. 避免每次局部修改都重建全模型或在多个库之间全量拷贝。
5. 尽量统一主视口的相机、深度、裁切、选择 ID 和高亮。多个渲染器共存需有明确收益，不能默认叠加。
6. “可替换”不等于首期建设通用插件框架；只保留少量稳定适配边界。

初步技术方向是服务端 C++ 数据/事务核心、VTK/ParaView 远程显示基线、OCCT 几何服务、按需要选择一个网格后端。客户端待选择：桌面路线优先 Qt；浏览器路线先评估 trame 以缩短远程显示原型周期。Python 可编排流程，不让其逐实体对象循环成为亿级热路径。语言、系统与最终技术栈仍属待论证建议。

### 7.1 桌面与浏览器的成本/交互比较

用户已明确暂不限定客户端，要求先比较。以下为基于组件边界的工程判断，而非已完成的性能对比。

| 维度 | Qt 桌面客户端 | 浏览器客户端 |
|---|---|---|
| 远程视口原型 | 要接入图像流、输入事件和服务端协议；Qt 控件成熟，但远程显示不是自动获得 | trame 能快速接通 VTK/ParaView，通常更适合第一轮链路验证 |
| 完整工程工作区 | 停靠、多窗口、快捷键、复杂树表与属性面板基础较完整 | 能实现，但复杂停靠、焦点、右键与快捷键需更多产品级打磨 |
| 三维流畅 | 远程渲染时主要受同一服务器和网络链路制约，不能只因是原生应用就保证更快 | 同样受服务器和网络制约；本地辅助显示还受浏览器资源预算约束 |
| 分发维护 | 客户端打包、升级、系统兼容和协议版本维护 | 免安装、集中更新；仍有浏览器兼容、缓存版本和前后端协议维护 |
| 文件与外部工具 | 本地文件、系统关联和工具启动更直接 | 文件上传/下载、服务器路径和权限需作为明确交互流程 |
| 平台自主性 | 自主界面与业务层，少量组件边界容易解释 | 可自主实现；使用 trame 时应限制它管理业务事务的范围，防止后期耦合 |
| 更适合的优先目标 | 长时间高密度专业操作、桌面工作区体验 | 访问便利、集中部署、远程分发、快速验证 |

当前建议：先用 trame 做可丢弃的远程显示/选择实验，验证相同数据、分辨率和网络下的延迟与准确性；产品客户端仍保留 Qt/浏览器二选一。原型采用 trame 不等于已经承诺整个产品用 Python 或 Web 开发。若已有明显偏好的使用方式，可以直接缩减另一条路线的研究，避免同时建设两个正式客户端。

服务端权威模型和编辑协议尽量独立于客户端；只在有实测收益时增加客户端局部缓存。第一轮不同时建设纯远程、全量本地和复杂混合三套实现。

## 8. Nastran 单模板仍需明确范围

Nastran 是求解器家族/格式生态的名称，不能只写“支持 Nastran”就视为格式需求完备。pyNastran 的 BDF API 本身区分 MSC/NX 等模式，这说明方言是实际集成变量。[API 依据](https://pynastran-git.readthedocs.io/en/latest/reference/bdf/pyNastran.bdf.bdf.html)

后续需确定：

- 方言、版本及首批分析序列；例如是否仅线性静力和模态，尚未确认。
- 壳/梁/实体、刚性连接、质量、材料、属性、约束、载荷、坐标系及工况的卡片清单。
- 小字段、大字段、自由格式、续行、INCLUDE、注释、编号和数值精度策略。
- 未知卡片：保留原文并标识未解释、阻止相关不安全编辑，或者明确拒绝；不得静默丢弃。
- 未知卡片引用已重编号实体时，单纯原样保留不再安全。需要限制重编号、理解依赖或阻止导出。
- 区分语义等价往返与逐字节原样保存；首版不应无意承诺后者。
- 卡片与引用校验、质量检查、目标求解器接受验证分开；通过另一解析器不等于求解一定可用。

## 9. 粗略 token 预算

预算口径：AI 辅助工作的累计输入与输出 token，包括多轮上下文、检索材料、工具返回、子代理和失败重试。下表是规划预留，不是本会话已测用量，不是账户额度，也不是开发工时或费用报价。重复上下文和是否命中缓存会影响实际计费，不能简单把总 token 直接换成价格。

假设：单一客户端路线（桌面或浏览器二选一）+ 服务端数据/渲染/事务，亿级既有模型导入与局部编辑，限定 Nastran 卡片集，几何/网格能力克制，不自研求解器，不含多人协作、完整后处理、全量自动网格生成。每阶段按独立增量列出，早期原型允许一次路线修正。

| 阶段 | 建议预留 | 交付与估算把握 |
|---|---:|---|
| 需求澄清与组件预研 | 10万—30万 | 分几轮完成需求草案、来源表、边界与验收；中低把握 |
| 架构与接口/测试方案 | 30万—80万 | 数据、远程显示、事务、协议、导入与存储边界；低把握 |
| 关键风险原型 | 150万—500万 | 大规模导入、远程显示/选择、局部修改、历史落盘及断线恢复；低把握 |
| 可用首版平台 | 500万—1800万 | 工程管理、Nastran 子集、编辑、检查、客户端/服务端与部署；很低把握 |
| 产品化与持续稳定性 | 500万—2500万 | 真实模型适配、恢复机制、网络与驱动差异、并发资源、性能与缺陷修复；很低把握 |

上述假设下可暂按 **约 1200万—5000万 token** 作为 AI 辅助研发总量级占位，不能作为固定总价或完成保证。若只是本轮初步分析，按第一行预留即可；单份报告正文通常只是数千至约一万 token，研究过程总量会更高。

更可靠的预算方法：完成一个代表性闭环“导入 → 浏览/精确选择 → 局部修改 → undo/redo → 导出”，记录实际各步骤输入/输出及返工原因，再据剩余可验收工作项重估。亿级目标未通过实机原型前，不宜把预算冻结。

token 无法替代真实测试数据、性能测试硬件、领域专家校核、手工交互验收或第三方授权成本。
