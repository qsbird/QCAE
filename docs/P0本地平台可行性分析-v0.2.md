# P0 本地 CAE 平台可行性分析 v0.2

> 历史讨论：本文件保留当时的分析与估算；当前开发依据为 [设计基线1.0](baseline/README.md)。冲突时不沿用本文件旧范围。

日期：2026-09-25。状态：需求与可行性分析，未进入代码实现。本文取代前两份报告中关于首期服务器部署、亿级验收和完整商软平台范围的建议；此前资料仅保留为研究记录。

## 1. 最新确认与总体判断

用户已确认：

- P0 暂不实现服务器大模型路线，先以本地中小模型完成平台闭环，亿级为后续目标。
- 保留前后端分离，优先保证底层模型与接口支持后续复杂功能。
- P0 实现限定的平台能力；界面保持必要程度，Nastran 分析准备以同一基础悬臂梁算例为限。
- 脚本与扩展为 P1，但 P0 提供相应底层接口。
- 其余能力当前不设计。本轮仍仅分析可行性。

结论：技术上可行，范围相比远程亿级平台明显收敛。减少的主要工作是远程显示、网络同步、分布式资源与超大模型容量适配。仍需认真完成的核心是实体与组织关系、统一查询、可撤销事务和持久化恢复。

“保留扩展能力”应体现为现在就能测试的边界，而不是完整设计未来系统。不能据此承诺未来亿级支持只需换一个通信适配器；数据分块、索引、显示缓存、传输与算法仍可能需要专项优化。

## 2. P0 逐项可行性

| 用户需求 | 可行性与主要成本 | 底层现在必须具备 | 可以简化的部分 |
|---|---|---|---|
| 必要工作区与命令发现 | 容易，依赖现成 UI 控件 | 命令标识、参数、启用条件与模型操作解耦 | 一个主视口、模型面板、属性表单、任务/消息区 |
| 部件/装配、材料/属性、集合、INCLUDE、多视角 | 可行，属于核心模型设计 | 分离不同组织关系、稳定实体身份、关系查询 | 用同一浏览器切换视角，暂不要求复杂工作区 |
| 多条件查询、框选、批选、隐藏/穿透、反选 | 可行，但不是低成本控件功能 | 可组合查询、选择域、实体类型、精确 ID、版本 | 列出有限 P0 条件；高级几何/拓扑条件不默认包含 |
| 基础显示 | 容易到中等 | 显示对象与业务实体映射、视图状态独立、局部刷新 | 基本相机、线/面显示、显隐、颜色、高亮 |
| 最小属性与表格编辑 | 容易到中等 | 强类型字段、引用语义、统一修改命令 | 悬臂梁相关表单，少量属性列表，不做通用复杂表格 |
| 引用与依赖 | 可行，但需最先落实 | 正向引用、反向查询、删除影响、未解析引用诊断 | 单文档内关系，基础合法性检查 |
| 最小 Nastran 分析准备 | 可行，受方言/卡片/求解器约束 | 节点、单元、材料、属性、载荷、约束、工况语义 | 只支持指定线性静力悬臂梁，不做其他分析范围 |
| 工程/BDF 导入导出、保存/另存 | 可行，正确性工作不可省 | 工程格式版本、稳定 ID、原子保存、INCLUDE 路径处理 | 支持明确子集的语义往返，不承诺所有 BDF 卡片 |
| undo/redo 与历史 | 可行，是核心工作 | 原子事务、准确差量、保存点、引用一致性、历史配额 | 线性历史即可，跨重启历史要求单独明确 |
| 基础检查 | 可行，算法范围可小 | 结构不变量、带版本的诊断结果、修复走事务 | 缺失引用、重复编号、非法字段、基本连接与算例检查 |
| 任务/取消/版本/资源/恢复 | 可行，但需明确恢复等级 | 任务状态、提交边界、读版本、资源计量、恢复记录 | 本地任务队列；中断任务识别后重启，不默认断点续算 |
| P1 脚本，P0 接口 | 可行，能减少后续重复开发 | 无 UI 的查询/修改/任务服务、稳定参数和错误码 | P0 不做脚本编辑器、录制器或插件系统 |

## 3. 前后端分离的最低有效实现

P0 建议先做逻辑分离，可以同进程运行；需要崩溃隔离或最终选择浏览器时，再评估本地独立进程。用户目前没有限定进程形式或客户端技术。

```text
必要界面 / 本地显示适配器
        ↓ 命令、查询、任务请求
应用服务边界（参数、稳定 ID、结果、版本、事件）
        ↓
文档核心 / 引用关系 / 查询 / 事务与历史 / 任务
        ↓
工程存储 / Nastran 导入导出 / 必要算法适配器
```

接口边界要求：

1. 界面只发出操作意图，不能直接写核心数据。
2. 核心不依赖 QWidget、浏览器状态或可变 VTK 场景对象；显示结构不是权威模型。
3. 参数/结果使用显式类型、稳定 ID、模型版本，避免传可写指针、UI 回调或依赖当前窗口的隐含上下文。
4. 批量操作是一次请求，不能设计为每节点/单元一次服务调用。
5. 读请求返回分页结果、选择结果句柄或受生命周期约束的只读数据块；进程内允许受控零拷贝，不必为“将来远程”在当前全量序列化。
6. 核心可由无界面测试程序调用，完成导入、查询、编辑、undo/redo、保存、导出。
7. 长任务使用非 UI 线程；任务状态和取消无需依赖 GUI 事件循环。

现在只实现本地适配，不设计远程协议、服务发现或分布式部署。无界面闭环测试是分离有效的主要证据。

## 4. 数据组织：不同关系不能压成一棵树

| 关系 | 用途 | 不能混用的语义 |
|---|---|---|
| 装配层次与部件归属 | 工程结构和操作范围 | 不等于求解器文件拆分；装配树调整不应隐式移动节点 |
| 集合成员 | 任意操作/检查/输出范围 | 一个实体可以参与多个集合 |
| 材料/属性/单元引用 | 求解器语义、依赖检查 | 被共享对象不应复制到每棵树下成为不同实体 |
| INCLUDE 文档组织 | 来源、保存位置与导出结构 | 不等于部件；文件拆分不能改变力学连接 |
| 显示状态 | 当前视图的可见性、颜色与高亮 | 不应删除业务实体或改变其求解器语义 |

建议稳定内部实体 ID 与 Nastran 外部编号、数组位置分离；外部编号按相应类别/命名空间校验，不把整个求解器模型的所有数字混为一套编号。节点可能被不同部件单元共同引用，不能强制以复制节点解决归属问题。

P0 数据表具有类型、实体身份和明确引用；网格大数组不逐实体依赖 UI 对象。容量计数、文件偏移与批量接口避免写死小范围，但不要求本轮完成亿级内存布局。

装配“层级组织”与“同一部件多个带变换实例”是不同工作量。建议 P0 的装配先定义为真实部件的层级组织；是否必须重复实例须在实施前确认，不在本轮延伸设计实例系统。

工程文件负责完整平台语义；BDF 负责所选求解器能表达的数据。部件名称、任意装配结构、界面状态等不能默认通过普通 BDF 完整往返。

## 5. 查询与选择：范围可广，但必须有限、可组合

建议 P0 条件清单：实体类型、ID/范围、名称、部件/装配范围、集合、INCLUDE、材料/属性及受支持字段、可见性、框选空间条件。支持 AND/OR/NOT、交并差；不必同时支持任意脚本、SQL 或全部拓扑推理。

需要明确：

- 隐藏：实体被用户/视图规则关闭显示；被遮挡：实体仍显示但在其他实体后面。二者独立。
- 穿透选择：通常表示忽略前方遮挡，不自动代表允许选择被主动隐藏的实体。
- 反选：相对于指定的候选域执行，例如“当前部件中所有可见梁单元”，不能隐含为整份文档的所有类型。
- 框选：指定完全包含或相交即可；使用明确相机/投影/视图状态，并返回真实实体 ID。
- 选择结果：绑定读取时的模型版本；修改命令提交时检查版本，避免对过期选择无声执行。

这些选择语义应在查询服务定义；渲染器只提供拾取或可见性加速。显示精度可以降低，最终选择必须准确。

## 6. Undo/redo、检查和任务共享一条修改路径

推荐核心路径：参数与引用校验 → 读取确定版本 → 计算候选变更 → 提交前版本校验 → 原子提交 → 历史记录与变更事件。

- P0 同一文档只允许一个修改提交者，多项只读任务可以基于稳定版本运行；不实现复杂并发合并。
- 字段修改、集合编辑、归属调整、创建/删除、引用变更都经过同一事务；批量操作整体成功或整体失败。
- undo 恢复精确旧值及关联，不单靠再次执行反向算法。操作合并可以用于连续拖动，但必须保持可验证的恢复结果。
- undo/redo 同样产生新的单调递增文档修订号，避免旧异步任务把“撤销回旧内容”误认为版本从未变化。
- 保存点与当前是否有未保存修改，按历史位置/内容状态判断，不能只比较单调版本号是否相等。
- 模型、引用索引、历史和持久化记录要协调提交；不能先修改模型，再因历史记录失败而留下不可撤销的半事务。
- 视图/选择历史与模型历史分开定义；导出到外部文件与外部求解作业不属于普通模型撤销。

如果使用 Qt，QUndoStack 可以帮助呈现撤销动作，但它的 push 会执行 redo，历史条数也不等于字节配额，不能再无条件套在已经执行的核心事务外层。[Qt 官方文档](https://doc.qt.io/qt-6/qundostack.html)

检查分两类：核心不变量在提交前强制校验，例如引用合法性、字段类型、实体存在性；模型诊断可在后台执行，例如连接问题、算例完整性。诊断结果带规则 ID、实体 ID、严重度、模型版本，版本变化后标记过期或重新检查。不要求 P0 通用规则 DSL 或自动修复平台。

## 7. 长任务、配额和会话恢复的最小边界

建议状态：排队 → 运行 → 提交 → 成功；另有取消请求、已取消、失败、中断。取消请求与已经取消不能混为一谈。

计算阶段合作式取消，未提交候选结果可丢弃。短暂原子提交阶段完成后返回准确状态，不承诺每个 CPU 指令都能打断。非可取消算法通过适配器暴露真实限制。

资源配额先落实到可控制的文档缓冲、显示缓存、撤销历史、任务并发和临时文件。采用预估、限制并发和超额拒绝；同进程第三方算法的所有分配不能仅靠计数器获得操作系统级硬隔离保证。若某算法需要强制终止或硬限额，可局部使用独立任务进程，不能因此把全平台提前做成分布式系统。

恢复层次必须区别：

1. 恢复最后成功保存的工程及必要工作区。
2. 从检查点/事务日志恢复已持久化但未手动保存的修改。
3. 恢复后继续撤销关闭前的历史。
4. 中断算法从中间步骤继续计算。

建议 P0 至少完成 1 和有明确持久化边界的 2；任务记录恢复后将未完成任务标为中断，允许重新执行。3 的历史保留量需确认；4 不默认包含。若保存确认意味着持久化成功，恢复测试就必须验证确认过的数据，不用“自动保存”模糊替代。

工程保存采用临时目标、验证和原子切换；多文件工程使用统一提交清单/版本指针等机制，不能假设逐个重命名就构成整体原子保存。另存时同步处理文档身份、相对 INCLUDE 路径和资源引用。具体存储实现等正式设计阶段确定。

## 8. 悬臂梁：可作为闭环，但不是全部平台验收

建议先采用一个线性静力一维梁算例：等截面直梁、一端固定、自由端横向力，明确单位、材料、截面惯性与局部方向。候选最小模型使用 GRID、CBAR/PBAR、MAT1、SPC1、FORCE 和相应工况控制；具体格式与卡片取决于指定 Nastran 方言/版本。PBAR 的材料、面积与截面参数关系可参照 [pyNastran 官方卡片文档](https://pynastran-git.readthedocs.io/en/latest/reference/bdf/cards/properties/pyNastran.bdf.cards.properties.bars.html)。最终以目标求解器文档及真实执行为准。

验收流程：导入/建立模型 → 修改载荷或截面 → 基础检查 → 导出 BDF → 使用指定现有 Nastran 求解器运行 → 核验位移和支反力 → undo/redo 后重新导出核验。

只生成一个看似合法的 BDF 不能称为“能跑分析”。可以外部命令行执行求解并读取少量数值，不要求新增完整求解器或后处理界面。位移参考值必须与梁理论、剪切变形、截面方向和单位一致，不能不加区分地使用简化公式。

同一物理算例还可有组织变体：梁划成多个逻辑部件，放入一个装配、多个集合和不同 INCLUDE，共享材料，并保持相同节点连接及物理结果。这可验证组织结构没有改变力学语义。

另外需要非求解型平台测试：隐藏/遮挡对象、跨文件引用、删除被引用材料、批量失败、任务取消、保存中断、恢复、过期结果。测试数据可以极小，不增加新的产品功能。

## 9. 建议实施顺序

| 顺序 | 交付 | 可行性证明 |
|---|---|---|
| A：最小文档与格式 | 稳定 ID、各组织关系、引用、最小 Nastran 子集、工程读写 | 无 UI 往返后语义一致；组织变化不改变悬臂梁物理模型 |
| B：事务与生命周期 | 命令、差量历史、保存点、任务状态、取消/版本检查、恢复 | 无 UI 验证批量原子性、undo/redo、故障恢复与资源上限 |
| C：查询与基础界面 | 多视角模型树、条件查询、框选/穿透/反选、基本显示、最小表单 | 所有界面编辑只走 A/B 接口，隐藏和选择语义测试通过 |
| D：真实分析闭环 | 同一悬臂梁编辑、校验、导出、已有求解器运行、数值核验 | 更改/撤销/重做后的输出与预期一致，无需复杂后处理 |
| E：P0 集成验收 | 中小模型分档、保存/另存/导入导出、任务与恢复场景 | 固定硬件上响应性、正确性、内存及历史体积有记录 |

核心接口与最低持久化边界从 A 开始定义，B 补齐失败路径。规模测试不延迟到最后才第一次运行。最终模型数量上限与目标机器尚未确定，不能用一个小梁算例推断“中小模型都流畅”。

## 10. 当前可以确认与仍需锁定的边界

可以确认：范围可行；本地中小模型为 P0；前后端逻辑分离；底层优先；脚本接口从 P0 建立；服务器与亿级验收不属于 P0；未列功能不设计。

正式实施前仍需锁定：

- Nastran 方言、可用求解器、梁单元还是壳/实体悬臂梁。本文建议一维梁作为最低成本路线，尚非用户指定。
- 装配是否只需层级组织，还是必须支持同一部件多个实例。
- 恢复允许丢失的未持久化窗口，以及重启后是否需要继续 undo。
- 输入是否限定于支持的卡片集；未知卡片应拒绝或明确保留策略，不能静默丢弃；导入现有工程时的编号冲突策略也需定义。
- 客户端类型、首发系统、基准机器与中小模型规模分档。

这些未定项不会阻止当前可行性结论，但会影响正式验收和工期。早先针对完整远程亿级平台的 token 总预算已不适用，不应继续沿用；新的 P0 预算应在上述边界明确、一个无界面闭环完成后校准。本轮不以无依据的缩减百分比代替估算。


后续预算与组件建议已按用户请求更新，见 [P0 token 预算与组件清单 v0.3](P0-token预算与组件清单-v0.3.md)。该预算为原型前的低置信度规划值，不改变本文已确认范围。
