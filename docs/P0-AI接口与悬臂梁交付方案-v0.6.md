## 2. 分成两项交付

### A. P0 必备的无界面底层

所有支持范围内的模型操作均通过可测试的服务接口执行。GUI、测试程序和未来 AI 适配器调用同一套接口；核心无需加载 Qt 窗口或 LLM SDK。

包括模型读写、组织、选择、属性/载荷/约束修改、依赖检查、undo/redo、任务和恢复。补充类型、单位、前置条件、稳定错误码、状态摘要、影响预览与证据记录。

### B. 最小 AI 交互验证

限定一个悬臂梁场景：自然语言收集输入 → 建模/修改 → 校验 → 指定已有求解器 → 位移/反力读取 → 解释与撤销。用户已确认：外部 AI 客户端调用软件工具接口，软件保留 GUI。

首版使用外部 AI 客户端接入工具接口：复用已有对话、模型接入和消息处理，软件提供 GUI 及可调用工具。内置聊天与仅做 API 是此前比较过的替代路线，不属于本次选定交付。当前不锁定任何 AI 厂商。

如果只选择 A，不宣称已完成面向非专业用户的 AI 软件。若选择 B，真实模型调用与真实求解器运行都要验收，不能只用模拟工具回放替代。

## 3. 应用接口分组

以下名称为业务契约示意，实际实现可以合并同类操作；它们不是对 MCP 方法名称的重新定义。

| 分组 | 示例能力 | 关键输出 |
|---|---|---|
| 能力 | capabilities.list | 卡片/分析/命令/格式支持范围，参数和单位 |
| 工程 | project.create/open/save/save_as；model.import/export | 工程身份、版本、资源标识、诊断 |
| 模型观察 | model.summary；entity.query/details/references | 有版本的摘要、实体/集合句柄、数量、分页结果 |
| 分析输入 | analysis.get_setup/update_inputs | 单位、事实、假设、来源、缺失项 |
| 变更 | changes.preview/commit | 确定的目标、共享影响、变更摘要、事务及新版本 |
| 历史 | history.list/undo/redo | 可撤销范围、保存点、撤销后的新版本 |
| 检查 | validation.run/get_issues | 规则、严重度、实体和输入版本 |
| 求解 | analysis.start/results | 导出输入摘要、job、运行配置、结果依据 |
| 任务 | jobs.get/cancel | 状态、进度、取消请求结果、失败原因 |
| 观察图像 | view.render_snapshot | 图片资源、相机、模型版本；非图形操作不依赖它 |

修改指令必须对应受支持的领域操作：赋属性、改截面、设载荷、设约束、修改集合等。不得暴露一个能直接执行 SQL/任意 shell 的通用后门作为 AI 常规接口。

## 4. 公共请求与响应契约

设计样例见 [结构化交互样例](contracts/p0-ai-examples.json)。样例不是可运行服务或完整协议 schema。

请求公共字段：

- api_version：应用契约版本，与传输协议版本分开。
- request_id：调用跟踪标识，每次请求独立。
- document_id：目标文档；实体 ID、版本标识按字符串传输，避免数值精度歧义。
- expected_revision：需要一致性保障的读取/修改所依据的文档版本。
- idempotency_key：有副作用请求的逻辑操作标识；重试沿用，新的操作使用新键。
- operation 与参数：显式类型、数值和单位、必要的坐标系及容差。

调用者身份与授权由宿主建立，不能信任 AI 在参数中自行填写的 actor 或 approved=true。记录的操作者来源由应用服务附加。

响应至少明确：success、needs_input、conflict、accepted 或 failed；并附请求标识、相关版本、结构化数据和诊断。修改成功返回 transaction_id；后台任务返回 job_id；缺信息返回字段及可理解的问题，无 GUI 模式不弹模态窗口。

### 预览与提交

预览把操作内容、目标集合、单位归一化结果、全部影响者和基础版本固定为 preview_id。提交引用该预览，核心检查是否过期以及当前授权；AI 不能通过修改提交参数偷偷改变已预览内容。

同一个幂等键、同样操作应返回同一既有结果。已提交请求的重试先识别既有提交，不能仅因 expected_revision 已旧就误报失败并促使调用方创建第二次修改。相同键却换了参数，应返回键冲突。

预览不是一律要求用户确认。已授权范围内的常规可逆编辑可以自动提交；必要物理事实有歧义或操作越出范围时才转为待输入。

### 三类版本

文档修订号用于避免并发/过期提交；每次修改或 undo 都递增。分析输入摘要用于判断结果是否仍适用于当前物理模型；纯视图变化不会使物理结果过期。视图版本记录相机与显隐，用于截图/图形拾取一致性。

不要因为模型回到旧内容就回退文档修订号；若输入摘要重新一致，旧结果能否复用还要同时检查求解器和运行配置等依据。

## 5. 最小数据补充

| 数据 | P0/AI 用途 |
|---|---|
| AnalysisIntent | 用户问题、希望获得的量、场景标识、支持范围 |
| Quantity | 数值、单位、量纲；方向/位置附坐标系 |
| InputEvidence | 来源类别、用户原始输入或资料引用、是否已确认 |
| Assumption | 理想化假设、适用依据、待确认项、对结果的限制 |
| ChangeRecord | 实际调用者、操作参数、影响摘要、事务与版本 |
| AnalysisRun | 输入快照摘要、求解器/版本、运行设置、输入/日志/结果资源 |
| CheckEvidence | 数值检查、规则版本、期望/实际值及容差、未完成原因 |

聊天全文不是物理模型的权威来源。经校验的事实和假设进入上述记录，模型和结果中的引用可追溯。AI 读取摘要和必要片段，不传送全部节点列表。

## 6. 一维悬臂梁工作流

建议场景为等截面直梁、线弹性、小变形静力、一个固定端和端部横向力。具体 Nastran 方言、卡片、截面以及理论校验方式仍按已有待定项锁定；本轮不扩展到任意结构。

流程状态建议：收集输入 → 输入就绪 → 预览就绪 → 模型已提交 → 检查完成 → 求解中 → 结果可用 → 解释完成。任何阶段可返回待输入或失败；修改分析相关输入后使后续检查/结果状态失效。该状态记录可恢复，不等于支持算法断点续算。

用户面对的问题应使用真实工程语言，例如尺寸单位、如何固定、施力大小与方向。专业术语映射由场景定义承担。材料未知、质量/力混淆、支承不明时，AI 不得自行填出一个可求解模型再宣称正确。

解释内容至少包括：输入事实、采用假设、计算量和单位、检查证据、未解决问题、对应模型/运行版本。工具成功退出、结果可读、数值检查通过分别显示；不能将三者压成一个“工程安全”结论。

## 7. 实施切片与停止条件

下面的路径是计划中的模块位置，不是当前已经存在的源文件。设计依据与现有文件链接见第 1 节。

| 切片 | 计划模块位置 | 完成条件 |
|---|---|---|
| S1 核心接口 | src/core、src/application、tests/contracts | 不加载窗口完成模型查询及一条原子修改/撤销；类型/单位/错误契约测试通过 |
| S2 状态与证据 | src/application、src/storage、tests/recovery | 来源、假设、版本和分析记录保存重开后保持一致 |
| S3 求解适配 | src/adapters/nastran、tests/integration | 指定真实求解器运行悬臂梁，结果读取和对应输入可核验；无可用求解器时该项未完成 |
| S4 工具入口 | src/adapters/ai 或独立 adapter 目录 | 选定 AI 入口可发现/调用工具，和 GUI 共用服务；不依赖任意脚本执行 |
| S5 引导与评测 | scenarios/cantilever、tests/ai | 缺参、修改、失败与越界用例通过；至少一次真实 AI + 真实求解端到端演示 |
| S6 联合回归 | tests/e2e、tests/ui | GUI/AI 切换、重试、取消、恢复、陈旧结果测试通过；限定场景可交付 |

先完成 S1 的无界面契约再编写 AI 编排，避免让提示词补救底层没有的能力。独立图像生成不是通过无界面建模验收的前置条件。

## 8. 组件影响

Qt、VTK、SQLite 仍按原建议负责界面、显示和存储。新增的是一个薄工具适配器、版本化的场景定义、求解/结果适配和评测数据；不引入多代理框架或通用工作流引擎。

如果采用 MCP，可选择与适配器语言匹配的官方 SDK；具体语言/版本在集成原型确定。本地进程或 stdio 接入不要求部署网络服务器。MCP 的工具描述可承载输入/输出 schema，但业务契约仍属于应用。[MCP 官方工具规范](https://modelcontextprotocol.io/specification/latest/server/tools)

如果外部 AI 客户端承担对话，可暂不新增软件内聊天面板或模型 SDK。已有 Nastran 求解器是独立必需验收依赖。结果读取可评估限定解析器或 pyNastran 工具适配，不在本轮无条件将 Python 变为产品运行依赖。

本地 CAE 并不自动等于 AI 数据也留在本地；实际数据流取决于选定客户端/模型。工具响应遵循摘要与按需读取，连接模型时明确数据去向。

## 9. 条件预算更新

以下针对已选定的外部 AI 入口，按“外部 AI 客户端 + 受控悬臂梁 AI 演示”方案估算，仍为低置信度累计输入/输出 token 规划。原 P0 无界面接口、基本事务、任务和悬臂梁外部验证已经计入 350万—700万，不再次收费式计入下表。

| AI 增量工作 | 额外预算，万 token |
|---|---:|
| 工具语义、结构化反馈、预览/幂等契约补强 | 20—40 |
| 引导场景、输入事实/假设/结果依据 | 20—40 |
| 求解启动与结果查询的自动化补齐 | 10—25 |
| 一个工具适配器与一个外部 AI 客户端接通 | 15—30 |
| AI 专项评测、真实端到端及异常交互 | 20—45 |
| 合计 | 85—180 |
| 加约 30% 风险预留后取整 | 120—250 |

与原 P0 相加为 **470万—950万**，规划可按 **500万—1000万** 看待。这不是已批准消耗或保证。若将来改变为仅做 API，应移除不再交付的 AI 增量；若改为内置聊天，应另计会话 UI、模型接入和凭据/中断体验等工作。

模型推理的运行成本与研发预算分开。首个实际工具适配和验收场景完成后，依据真实调用量重估。

## 10. 风险及当前开放项

- 接口有调用但没有语义：以实际返回的单位、对象、影响、错误契约测试解决。
- 流程能结束但结论不可信：以真实求解、来源记录、独立检查和明确未完成状态解决。
- 人机交替造成陈旧操作：以版本检查、预览绑定、幂等提交及分析输入摘要解决。
- 假设随聊天漂移：以版本化输入与假设记录解决。

待用户/环境确定：具体外部 AI 客户端、目标求解器及可用环境、首次系统/硬件、恢复历史等级。已确认的本地中小模型、GUI与无界面共用业务核心保持不变。具体异常验收见 [P0 AI 验收用例](P0-AI验收用例-v0.6.md)。


后续模块、运行时与持久化设计见 [架构 v0.7](architecture/README.md)。v0.7明确本地独立engine、文档epoch和保存/恢复规则；本文件的旧调用样例仍为早期设计示意。
