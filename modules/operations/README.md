# qcae_operations

A pure C++20 operation registry and generated typed wire contracts. The registry owns handler registration and discovery metadata. `Value` is a transport DTO; it is never document authority and has no Qt, domain, application or persistence dependency.

Public API: `qcae/operation_registry.hpp` and generated `qcae/operation_inputs.hpp`. Link `qcae_operations`; its direct dependencies are `qcae_foundation` and `qcae_contracts`.

`schemas/operations/basic.json` is the authoritative schema for seven input contracts: material creation, modulus change, section creation, node movement, beam section assignment, line creation and line meshing. Explicit operation/schema IDs, versions and field IDs define persistent contract identity. The generator sorts operations by operation ID and fields by field ID, so JSON declaration ordering does not change generated bytes. It emits typed structs, `InputTraits<T>::definition/from_value/to_value`, and a normalized schema digest. It rejects duplicate operation/schema/type/field IDs, duplicate JSON keys and unsupported field definitions. A schema may declare `fields: []` for a parameterless operation; its generated adapter still requires an empty object and rejects extra members. Generation requires the already-used Python runtime and no new packages. CMake tracks every JSON file in `schemas/operations` and the directory membership, so schema additions, edits and removals regenerate the header on the next build without manual reconfiguration.

```sh
python3 tools/generate_operation_contracts.py schemas/operations build-core/generated/qcae/operation_inputs.hpp
python3 tools/generate_operation_contracts.py schemas/operations build-core/generated/qcae/operation_inputs.hpp --check
```

`OperationRegistry::register_typed<Input>(InputTraits<Input>::definition(), handler)` installs a callable accepting `const OperationContext&` and `const Input&` and returning `Result<Value>`. Generated metadata must match exactly. Duplicate operation IDs and input schema/type tokens are rejected. An empty callable cannot register. `descriptors()` derives availability from the entry's installed callable; there is no separate supported-operation list. `declare_unavailable(definition, reason)` publishes a future capability with no handler, and invocation returns `unsupported_capability`. Registrations/declarations are immutable entries: declaring and registering the same operation twice is an error.

`OperationContext` carries the trusted caller, optional document/revision, idempotency key, optional expected profile, request ID and optional requested version. `invoke(id, requested_version, context, value)` checks the installed version and required context before decoding. `invoke(id, context, value)` uses the contextual version if provided, otherwise deliberately selects the installed version for existing local callers. Both overloads forward the resolved version in the handler context; contradictory explicit/contextual versions are rejected. Neither overload invents required document/profile context. Every invocation requires a caller, including read-only or unavailable declarations. Document/epoch/revision/key/profile presence is checked only when declared; application services own actual identity/revision/profile/authentication comparisons. Generated decoding rejects unknown/missing fields, wrong object/string/integer/vector types, nonfinite/subnormal numbers, numeric integers outside the exact double input range, empty entity IDs and nonpositive/out-of-range segment counts. Missing or empty quantity units return `needs_input/missing_input`; unknown or dimension-mismatched unit choices return `invalid_unit`. Pressure quantity units stay explicit (`Pa`, `kPa`, `MPa`, `GPa`); service handlers use parameters to normalize units and enforce engineering constraints. Three-coordinate fields are explicitly canonical millimeters. Successful callback output must be an object; structured service errors retain their status/code.

Effect and document/epoch/revision/idempotency/profile context flags are schema metadata. The optional expected_profile schema flag defaults false when omitted. The hosting service validates context and performs transactions, identity/reference checks, resource limits, physical validation and history. The registry does not claim that a typed callback is an engine implementation or that a wire DTO validates engineering truth. Handler exceptions remain the service host's responsibility. Composition registers handlers before use; concurrent mutation of the registry is unsupported.

`features/materials` and `features/mesh_editing` install real typed handlers through `register_handlers(registry, app)`. Their plan factories normalize quantities, validate generated record rules and prepare private `EditSession` changes. `RecordApplication::execute` checks the plan signature, owns document/epoch/revision checks, allocates stable identities and commits history and retained operation receipts. Create output uses `receipt.primary_entity`, including idempotent replay after undo; handlers do not derive an identity from the request or rescan the model. Beam assignment sorts its unique selected IDs for set-semantic signatures and prepares the entire assignment before publication. Geometry and meshing handlers are composed by the engine using their own feature/runtime services.

`change_receipt_value` projects the shared receipt DTO for typed features and the engine: `transaction_id`, exact decimal-string `committed_revision`/`current_revision`, `replayed`, and `entity_id` when a primary entity exists. Decimal strings preserve the full unsigned revision range across JSON clients; the helper performs no document work.

The generated input metadata alone never advertises an installed engine implementation. Engine composition uses registry descriptors for availability; the older `docs/contracts/operations.json` still provides the catalog for remaining legacy operations.

After root target/test registration:

```sh
cmake --build build-core --target qcae_operation_registry_tests qcae_model_operation_tests
ctest --test-dir build-core --output-on-failure -R '^(operation_registry|generated_operation_inputs|model_operations)$'
```

The registry suite covers typed invocation, duplicate IDs/tokens, truthful availability, disabled future operations, version rejection, required context and distinct per-call forwarding, mechanical input failures before callbacks, generated round trips and output/error envelopes. The model operation suite exercises the real application coordinator and typed record handlers: canonical pressure units and optional Poisson values, stable create IDs on replay, retained receipt identities across coordinator reconstruction, epoch/revision conflicts, undo/redo, node movement, section creation, selected-beam assignment and atomic reference failures. Its retained store is a test double; actual SQLite and IPC integration require their corresponding suites. These focused checks do not establish full SK-04 or P0 acceptance.
